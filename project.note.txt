# Desain Database & Workflow Subcontract Management – RAB-Project

Keputusan desain ditetapkan

Tiga keputusan Anda menjadi dasar rancangan:

1. SPK mencakup pekerjaan internal dan pekerjaan Subcon.
2. Pembayaran Subcon hanya berdasarkan progres pekerjaan yang selesai dan lolos inspeksi.
3. Kepemilikan material sisa mengikuti sumber materialnya. Kepemilikan hanya berubah melalui transaksi jual-beli yang sah.

Saya juga menemukan bahwa repository `rab-project` pada branch `main` sebenarnya sudah memiliki fondasi modul Subcon. Ada tabel `subcontractors`, `subcon_contracts`, `subcon_contract_tasks`, `subcon_progress`, `subcon_progress_dtl`, `subcon_payments`, serta tabel invoice dan pembayaran invoice. Jadi, rancangan ini tidak akan membuat modul Subcon kedua dari nol. Kita perlu menyempurnakan dan menghubungkan fondasi tersebut dengan SPK, inspeksi, inventory, dan keuangan.

File dasar yang ditemukan:

- [subcon.sql](https://github.com/esusanto818/rab-project/blob/main/subcon.sql?utm_source=chatgpt.com)
- [subcon_invoice.sql](https://github.com/esusanto818/rab-project/blob/main/subcon_invoice.sql?utm_source=chatgpt.com)
- [spk_usage_ppn.sql](https://github.com/esusanto818/rab-project/blob/main/spk_usage_ppn.sql?utm_source=chatgpt.com)

## 1. Arsitektur modul yang diusulkan

SPK menjadi dokumen utama untuk mengendalikan pekerjaan. Perbedaan pekerjaan internal dan Subcon ditentukan oleh jenis SPK, bukan dengan membuat dua sistem SPK yang berjalan sendiri-sendiri.

PROYEK

RAB · Task · Sub-task · Anggaran

SPK – Dokumen Pekerjaan

SPK Internal atau SPK Subcon

SPK Internal

Pelaksana internal, mandor, tim sendiri

Pelaksanaan → Inspeksi → Progres proyek

SPK Subcon

Dikerjakan pihak Subcon

Pelaksanaan → Inspeksi → Sertifikat prestasi → Pembayaran

Kontrol Material & Kepemilikan

Material perusahaan · Material Subcon · Material campuran · Sisa material

Prinsip penting: SPK internal dan SPK Subcon menggunakan kontrol task, progres, inspeksi, dan histori yang konsisten. Namun, hanya SPK Subcon yang menghasilkan kewajiban pembayaran kepada pihak eksternal.

## 2. Desain database

### A. Tabel yang sudah ada dan peran barunya

| Tabel existing            | Peran dalam rancangan                         |
| ------------------------- | --------------------------------------------- |
| `spk`                     | Dokumen SPK utama, ditambah jenis SPK         |
| `spk_items`               | Rincian material untuk kebutuhan issue gudang |
| `subcontractors`          | Master perusahaan/orang Subcon                |
| `subcon_contracts`        | Ketentuan kontrak Subcon yang terkait ke SPK  |
| `subcon_contract_tasks`   | Pembagian nilai kontrak ke task               |
| `subcon_progress`         | Pengajuan prestasi/progres Subcon             |
| `subcon_progress_dtl`     | Rincian progres per task                      |

| `subcon_invoice_payments` | Pembayaran invoice                            |
| `material_out_header`     | Pengeluaran material perusahaan               |

Ada satu masalah desain yang perlu diperbaiki: saat ini `spk` dan `subcon_contracts` menyimpan identitas kontrak/SPK secara terpisah. Saya sarankan `spk` menjadi dokumen induk, sedangkan `subcon_contracts` menjadi detail komersial khusus SPK Subcon. Jangan menghapus tabel lama sebelum migrasi dan data historisnya direkonsiliasi.

### B. Perubahan tabel SPK

Rincian pekerjaan sebaiknya dipisahkan dari rincian material gudang. Buat tabel baru:

`spk_work_items`

Dengan pemisahan ini, `spk_items` tetap dapat menjalankan fungsi material untuk pengeluaran gudang, tanpa tercampur dengan kuantitas pekerjaan dan nilai kontrak.

### C. Progres dan inspeksi

Tabel `subcon_progress` dan `subcon_progress_dtl` dipertahankan sebagai pengajuan prestasi. Namun, status persetujuan prestasi tidak boleh menjadi satu-satunya bukti bahwa pekerjaan lolos inspeksi.

Tambahkan:

`subcon_inspections`

| Kolom             | Fungsi                                   |
| ----------------- | ---------------------------------------- |
| `id`              | ID inspeksi                              |
| `spk_id`          | SPK yang diperiksa                       |
| `progress_id`     | Pengajuan progres terkait                |
| `inspection_date` | Tanggal inspeksi                         |
| `inspector_id`    | Pemeriksa                                |
| `status`          | `DRAFT`, `PASSED`, `PARTIAL`, `REJECTED` |
| `notes`           | Catatan inspeksi                         |
| `approved_at`     | Waktu persetujuan                        |

`subcon_inspection_items`

| Kolom                | Fungsi                       |
| -------------------- | ---------------------------- |
| `id`                 | ID detail inspeksi           |
| `inspection_id`      | Header inspeksi              |
| `progress_detail_id` | Baris progres yang diperiksa |
| `qty_claimed`        | Kuantitas diajukan           |
| `qty_passed`         | Kuantitas lolos              |
| `qty_rejected`       | Kuantitas ditolak            |
| `rework_required`    | Apakah perlu perbaikan       |
| `inspection_notes`   | Catatan per item             |

Kuantitas yang lolos harus disimpan sebagai angka yang disetujui, bukan sekadar persentase. Ini penting untuk pekerjaan yang bisa diperiksa sebagian.

### D. Pembayaran berdasarkan hasil inspeksi

Pertahankan tabel invoice dan pembayaran yang sudah ada. Tambahkan satu lapisan dokumen yang menjadi dasar hak tagih Subcon:

`subcon_payment_certificates`

| Kolom              | Fungsi                                               |
| ------------------ | ---------------------------------------------------- |
| `id`               | ID sertifikat pembayaran                             |
| `contract_id`      | Kontrak Subcon                                       |
| `progress_id`      | Pengajuan progres                                    |
| `certificate_no`   | Nomor sertifikat                                     |
| `gross_approved`   | Nilai pekerjaan yang lolos                           |
| `retention_amount` | Retensi                                              |
| `dp_recovery`      | Pengembalian/pemotongan DP                           |
| `other_deductions` | Potongan lain yang sah                               |
| `tax_amount`       | Pajak                                                |
| `net_payable`      | Nilai bersih yang dapat dibayar                      |
| `status`           | `DRAFT`, `APPROVED`, `INVOICED`, `PAID`, `CANCELLED` |

Tambahkan `subcon_payment_certificate_items` untuk menyimpan rincian nilai per item pekerjaan dan inspeksi.

Aturan wajib: invoice Subcon tidak boleh menciptakan hak tagih baru di luar nilai sertifikat pembayaran yang telah disetujui. Invoice menjadi dokumen penagihan, bukan bukti bahwa pekerjaan telah diterima.

Perhitungan dasarnya:

\\[ \text{Nilai Prestasi} = \sum(\text{Qty Lolos Inspeksi}\times\text{Harga Satuan}) \\]

\\[ \text{Net Payable} = \text{Nilai Prestasi}+\text{Pajak} -\text{Retensi}-\text{Recovery DP}-\text{Potongan} \\]

Persentase DP, retensi, pajak, dan potongan harus mengikuti kontrak serta ketentuan yang berlaku. Tidak boleh ditetapkan sebagai angka global yang sama untuk semua SPK.

### E. Material dan kepemilikan

Setiap rincian pekerjaan perlu mengetahui siapa yang menyediakan materialnya.

| Mode      | Arti                                 | Dampak inventory                            |
| --------- | ------------------------------------ | ------------------------------------------- |
| `COMPANY` | Material disediakan perusahaan       | Issue dari inventory perusahaan             |
| `SUBCON`  | Material disediakan Subcon           | Tidak masuk stok perusahaan secara otomatis |
| `MIXED`   | Sebagian perusahaan, sebagian Subcon | Kuantitas dipisah menurut sumber            |

Untuk mode `MIXED`, buat rincian kuantitas per sumber, bukan hanya satu label.

Tabel baru: `spk_material_supply`

- `spk_work_item_id`
- `material_id`
- `supplier_type` (`COMPANY` / `SUBCON`)
- `supplier_id` (jika Subcon)
- `planned_qty`
- `accepted_qty`
- `unit`
- `ownership_transfer_rule`

Dengan demikian, material yang dibeli atau dibawa Subcon tidak otomatis dianggap sebagai stok milik perusahaan.

### F. Material sisa dan transaksi jual-beli

Saya sarankan menggunakan satu tabel induk untuk mencatat sisa material dan beberapa tabel transaksi untuk perpindahan kepemilikan.

`material_leftovers`

| Kolom                | Fungsi               |
| -------------------- | -------------------- |
| `id`                 | ID material sisa     |
| `project_id`         | Proyek asal          |
| `spk_id`             | SPK asal             |
| `material_id`        | Jenis material       |
| `source_owner_type`  | `COMPANY` / `SUBCON` |
| `source_owner_id`    | Pemilik asal         |
| `qty_detected`       | Kuantitas ditemukan  |
| `qty_available`      | Kuantitas tersedia   |
| `condition`          | Kondisi barang       |
| `current_owner_type` | Pemilik saat ini     |
| `location`           | Lokasi barang        |
| `status`             | Status penanganan    |

Tabel transaksi yang diperlukan:

- `leftover_transactions`: riwayat transaksi dan perubahan status.
- `leftover_purchases`: pembelian sisa material dari Subcon.
- `leftover_sales`: penjualan sisa material milik perusahaan kepada klien.
- `leftover_price_approvals`: referensi harga pasar, harga transaksi, alasan diskon, dan persetujuan.
- `leftover_inventory_movements`: penghubung transaksi dengan mutasi inventory yang sah.

Jangan mengubah kepemilikan hanya dengan mengubah kolom `current_owner_type`. Setiap perubahan harus mempunyai dokumen transaksi, nilai, tanggal, pihak penjual/pembeli, persetujuan, dan jejak mutasi.

## 6. Tahapan implementasi yang saya rekomendasikan

Jangan mengerjakan semua modul sekaligus. Urutannya harus mengikuti ketergantungan data.

1. Tahap 1 — Konsolidasi SPK

   Satukan konsep SPK Internal dan SPK Subcon. Hubungkan SPK dengan task, rincian pekerjaan, dan kontrak Subcon tanpa merusak proses Warehouse Issuing.

   Prioritas pertama
2. Tahap 2 — Progress & Inspection

   Bangun pengajuan progres, inspeksi per item, kuantitas lolos, kuantitas ditolak, dan rework.
3. Tahap 3 — Payment Certificate

   Hubungkan hasil inspeksi dengan sertifikat prestasi, invoice, DP, retensi, dan pembayaran.
4. Tahap 4 — Material Supply & Leftover

   Implementasikan material perusahaan/Subcon/campuran, pengembalian, pembelian sisa dari Subcon, serta penjualan sisa kepada klien.
5. Tahap 5 — Laporan dan audit

   Buat laporan nilai SPK, progres lolos inspeksi, hutang Subcon, retensi, penggunaan material, serta histori kepemilikan material.

## 7. Hal yang harus diperiksa sebelum membuat migration SQL

Ada beberapa ketidaksesuaian yang perlu diselesaikan dari fondasi repository:

1. `spk` saat ini berfungsi sebagai dokumen SPK yang juga berhubungan dengan pengeluaran material, sedangkan `subcon_contracts` menyimpan nomor dan nilai kontrak sendiri. Relasi keduanya perlu ditentukan dan data lama dipetakan.
2. `subcon_progress_dtl` saat ini memakai persentase kumulatif dan nilai task. Belum cukup untuk menjadi bukti kuantitas pekerjaan yang lolos inspeksi.
3. `subcon_invoices` dan `subcon_invoice_payments` sudah ada. Kita harus memperluas integrasinya, bukan membuat sistem pembayaran invoice kedua.
4. Skema database aktual perlu diperiksa untuk tipe ID, foreign key, struktur jurnal, dan mekanisme inventory. Saya belum menjalankan migration terhadap database PostgreSQL Anda.
5. Hak akses, approval, dan pembatalan transaksi harus mengikuti pola aplikasi yang sudah ada.

Keputusan desain yang saya rekomendasikan: gunakan `spk` sebagai induk SPK internal dan Subcon, `subcon_contracts` sebagai detail kontrak Subcon, dan `subcon_payment_certificates` sebagai satu-satunya dasar resmi pembayaran prestasi.

Langkah teknis berikutnya adalah membuat dokumen spesifikasi database final beserta migration SQL yang kompatibel dengan PostgreSQL versi aplikasi, setelah seluruh struktur tabel aktual diverifikasi. Saya akan menjaga perubahan tetap di branch pengembangan terpisah dari `main`, dan tidak menerapkan migration ke database produksi tanpa pengujian staging.
